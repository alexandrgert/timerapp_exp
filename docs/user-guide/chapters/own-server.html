Статус: отдельный вариант для тестирования. Серверная разработка ведётся в ветке pwa/selfhost-sync. Действующая GitHub Pages PWA продолжает использовать GitHub-синхронизацию; она автоматически на ваш сервер не переключается. Перед установкой нужен проверенный серверный выпуск. На момент обновления инструкции тестовый архив GitHub Actions ещё не выпущен, проверка настоящего HTTP/Service Worker остаётся обязательным этапом перед выдачей архива.

В этом варианте ваш сервер раздаёт приложение и хранит общий документ задач в SQLite. GitHub-токен для обмена не нужен. Первый выпуск рассчитан на одного владельца и несколько его устройств: администратор выдаёт отдельный отзывной ключ каждому устройству. Регистрации пользователей и входа по логину/паролю пока нет. Простое размещение обычных файлов GitHub Pages на VPS не добавит серверную синхронизацию — нужен именно серверный вариант.

Что потребуетсяТребование
VPS с LinuxНачальный ориентир для личного использования: 1–2 CPU, 2 ГБ RAM, 20 ГБ SSD.
Домен и доступОтдельный поддомен, управление DNS и SSH для настройки.
Runtime и HTTPSNode.js 24 LTS и reverse proxy Caddy или Nginx. Размещение в корне отдельного адреса, не в подпапке.
Постоянное хранилищеЛокальный диск для SQLite вне публичных файлов и каталога выпуска.
Резервные копииСогласованные копии SQLite и отдельное место хранения за пределами VPS.
  1. Получите проверенный серверный выпуск. Используйте архив tasktimer-selfhost из успешного согласованного запуска GitHub Actions. Сверьте SHA256. Он должен содержать pwa/selfhost/, общий сервер, публичные файлы и руководство. Архив прежней desktop-версии и обычная статика Pages не подходят.
  2. Подготовьте сервер. Создайте пользователя службы, каталог версий приложения и отдельный постоянный каталог данных. Установите Node.js 24 LTS. Подробные команды, пример systemd и порядок обновления находятся в pwa/selfhost/README.md внутри исходников и серверного архива.
  3. Настройте домен и HTTPS. Направьте поддомен на VPS, включите сертификат и автоматическое продление. Reverse proxy передаёт запросы приложению; внутренний порт приложения закройте от внешней сети. PWA и API должны работать на одном адресе, например https://timer.example.org/ и /api/sync.
  4. Запустите серверный entrypoint. Используется node pwa/selfhost/server.cjs, а не обычный статический сервер. Обязательные параметры: PORT, CLOUDCLI_DATA_DIR — абсолютный путь постоянного каталога, и TASKTIMER_PUBLIC_ORIGIN — ваш HTTPS-адрес без завершающего слеша. SQLite не должна попадать в Git, архив программы или публичный каталог. Для разработки HTTP допускается только на loopback.
  5. Создайте ключи устройств. На сервере от имени службы с тем же CLOUDCLI_DATA_DIR выполните node pwa/selfhost/admin.cjs add-device 'Мой телефон', затем отдельно для компьютера. Команда показывает ключ один раз. Передайте его владельцу устройства защищённым способом; в переписку с агентом и журналы CI ключ не отправляйте. Для списка устройств используется devices, для отзыва — revoke DEVICE_ID.
  6. Подключите первое устройство. Откройте новый адрес → настройки → «Синхронизация со своим сервером». Введите ключ устройства, нажмите «Проверить подключение», затем «Синхронизировать». На личном устройстве можно включить «Запомнить ключ на этом устройстве».
  7. Перенесите данные выбранным способом. До перехода закончите обмен в старой PWA и скачайте JSON-копии с каждого устройства. Для отдельного теста импортируйте копию один раз на первом устройстве новой PWA и выполните обмен. На остальных устройствах получите данные синхронизацией, не повторяйте импорт одной копии.
  8. При необходимости сохраните всю причинную историю. Это отдельный административный перенос: после финального старого обмена получите data/state.v2.json из своего приватного репозитория. На пустой серверной базе выполните node pwa/selfhost/admin.cjs import-v2 /private/exported-state.v2.json. Команда проверяет формат, сохраняет ID и историю удалений и отказывается писать в непустую базу. Это альтернатива JSON-импорту, а не следующий шаг после него. Не редактируйте v2 вручную и не запускайте два независимых обмена одной базы одновременно.
  9. Подключите второе устройство. Откройте тот же новый адрес, введите его собственный ключ, выполните обмен. Сверьте задачи, приоритеты, сессии, комментарии и удаления. Включите автоматическую синхронизацию отдельно на каждом устройстве: через 10 секунд после изменений, каждые 2 минуты в видимом приложении и при возвращении сети.
  10. Проверьте перед постоянным использованием. Проверьте одновременные изменения с двух устройств, явное разрешение конфликта, удаление сессии, офлайн-работу, перезапуск сервера, отзыв ключа и восстановление резервной копии в отдельном экземпляре. Новый адрес означает отдельную установленную PWA. Старое приложение и GitHub-репозиторий сохраните до успешной сверки.
  11. Настройте копии базы. Команда node pwa/selfhost/admin.cjs backup /absolute/backup/new-copy.sqlite создаёт согласованную копию при работающем сервере. Настройте регулярное выполнение и перенос копий за пределы VPS. Не копируйте только основной файл работающей SQLite в WAL-режиме. Проверку восстановления проводите отдельно, не поверх рабочей базы.
  12. Обновляйте код отдельно от данных. Сначала резервная копия, затем новый проверенный каталог выпуска и перезапуск службы. Сохраняйте предыдущий код для отката, учитывайте совместимость схемы базы. Приложение сохраняет механизм баннера обновления; размещённая версия и release notes должны обновляться вместе.

Ключи и данные. «Забыть ключ» удаляет его из браузера, но не отзывает на сервере. При потере устройства администратор должен отозвать его ключ. Отзыв прекращает дальнейший обмен, но уже загруженные задачи остаются на устройстве. Ключи не входят в JSON-копию и документ обмена; сервер хранит их хеши. Это защита доступа, а не шифрование задач на диске.

Границы варианта. Закрытая или свёрнутая PWA не получает гарантированного фонового выполнения только из-за переноса на VPS. Распознавание речи остаётся на устройстве. Нет веб-панели администрирования, отдельных баз независимых пользователей или серверного push. Ответственность за домен, обновления, диск и резервные копии переходит владельцу сервера.
