# Объявление обновления PWA

Опубликовано 5 октября 2026 года: [GitHub Actions 37312857566](https://github.com/alexandrgert/timerapp_exp/actions/runs/37312857566), commit `e2c2e894e6f20657c6e7a344ee2b3aab8f625e2e`. На главном экране появляется блок «Доступно обновление» со списком изменений, кнопками «Обновить» и «Позже». Первая установка не считается обновлением.

Описание относится к установленному, но ожидающему активации Service Worker. Страница запрашивает его через MessageChannel; worker читает только собственный кеш. JSON со списка файлов текущего сервера или из кеша активной старой страницы для этого не используется. Worker сравнивает revision метаданных со своей ревизией. Если файл относится к другой публикации, повреждён, отсутствует или worker не отвечает за 2,5 секунды, показывается обычное предложение обновить без неподтверждённого списка изменений.

«Позже» скрывает эту ревизию в текущей вкладке/сессии; обновление остаётся доступным в настройках. Следующая ожидающая ревизия появляется снова. Проверка обновлений выполняется при открытии/возвращении к приложению, восстановлении сети и каждые пять минут, пока страница видима и устройство онлайн. Браузер может приостанавливать фоновую работу.

«Обновить» по-прежнему требует подтверждения пользователя и успешного завершения сохранения данных. Ошибка сохранения отменяет активацию и показывается в блоке, а также в настройках. Если ожидающая версия успела смениться, требуется новое подтверждение. Другие вкладки принудительно не перезагружаются.

## Как подготовить следующий выпуск

1. Обновить `public/release-notes.json` вместе с изменениями приложения **для каждого выпуска**. Описание должно касаться именно этого предстоящего выпуска, а не общего списка возможностей или предыдущего релиза.
2. Указать `title` длиной 1–150 символов и `changes` из 1–8 строк длиной 1–400 символов каждая. Это простой текст: HTML не выполняется, ссылки и Markdown не форматируются. Не записывать секреты или сведения о данных пользователя.
3. Не задавать ревизию вручную. GitHub Pages staging подставляет полный SHA публикуемого коммита; Node-сервер вычисляет ревизию по исходникам раздаваемой оболочки. В JSON и Service Worker должна оказаться одна ревизия. Это защищает от показа описания другой версии при смене файлов на сервере во время установки.
4. Выполнить проверки и отдельно согласовать публикацию. Метаданные включены в allowlist Pages, Node-сервера и Service Worker. Необязательная загрузка описания не блокирует установку исправной оболочки.

Пример структуры исходного файла:

```json
{
  "title": "Краткое название этого обновления",
  "changes": ["Что изменилось для пользователя", "Какое неудобство исправлено"]
}
```

## Первое обновление до версии с блоком

Уже опубликованная старая оболочка ещё не умеет показывать новый блок. В описание этого выпуска включено пояснение для пользователя: «Этот выпуск установите через ⚙ → „Приложение и хранение“ → „Обновить приложение“. После установки уведомления о следующих выпусках появятся на главном экране». Публикация сама по себе не добавляет элементы интерфейса в уже закешированную старую страницу.

## Проверки и ограничения

Все 88 обычных сценариев прошли локально и в разрешённом GitHub запуске, без ошибок и пропусков; результат подтверждён скачанным артефактом с проверенной SHA-256. Проверки обработчиков Service Worker подтверждают чтение собственного кеша и отказ от метаданных другой ревизии. Браузерные проверки с имитацией регистрации проверяют описание, «Позже», возврат новой версии, отсутствие блока при первой установке, безопасный текст, таймаут, подтверждение, сохранение, отказ при ошибке и смене ожидающего worker.

Настоящая проверка TCP/Service Worker в `tests/live-offline.check.cjs` прошла в том же разрешённом GitHub Actions запуске перед публикацией: две ожидающие ревизии, кешированные описания, «Позже», обновление с сохранением таймера и отсутствие принудительной перезагрузки другой вкладки. Локальная попытка остановилась до браузера из-за недоступности TCP-сервера. Проверка в GitHub устранила этот пробел; это проверка на тестовом TCP-origin, а не на физическом телефоне.

Отдельная проверка постоянного публичного HTTPS без подмены запросов подтвердила одинаковую ревизию SW и метаданных, пояснение первого обновления, отсутствие ложного предложения при первой установке и настоящую офлайн-перезагрузку с сохранением задачи и активной сессии. Следующая публичная версия ради проверки уведомления не создавалась: появление блока и обновление между версиями проверены в GitHub. Принятие этого обновления на устройстве пользователя ещё требует ручной проверки.

Журналы и снимки расположены в корне проекта в `documents/pwa-update-notice/`.
